# 第二轮基准：抗优化内核 —— TzdLang (JIT) vs Java 20 vs Node(V8) vs Python 3

> 本轮目标是补充第一轮（见 RESULTS.md）未覆盖的维度，且所有内核设计为**优化器无法折叠/跳过**：
> 含顺序状态依赖的 LCG、哈希操作、对象分配与动态分发、内存交换排序。
> 四种语言算法严格等价，校验值全部一致：
> `stringBuild len=128890`、`monteCarlo pi=3.142284`、`mapOps sum=19999900000`、
> `oop sum=66468878689`、`qsort min=1104 max=999999375 fill=141058334721867`。

## 测试内核

| 内核 | 规模 | 说明 | 考察点 |
|---|---|---|---|
| `stringBuild` | 20,000 次追加 | 累积式 `s = s + toString(i) + "-" + toString(i%7)`（注：不可变字符串语言为 O(n²) 拷贝） | 字符串拼接/增长策略 |
| `monteCarlo` | 1,000,000 次 | Lehmer LCG（x = x·16807 mod 2³¹−1，顺序状态依赖）+ 圆内判定 | 整数算术 + int→float + 分支 |
| `mapOps` | 200,000 条 | 字符串键 map 插入 + 全量回读求和 | 哈希表 + 字符串键 |
| `oop` | 200,000 次 | 4 步 LCG 生成坐标 → 2 次对象分配 + 虚方法调用 | 对象分配 + 动态分发 |
| `qsort` | 300,000 元素 | LCG 填充 + 手写 Lomuto 快排（全局数组 + 递归 + 交换） | 递归 + 数组随机访问 |

每个内核自带高精度计时（仅测计算），各跑 3 次取**中位数**。源码：`bench/tzd/round2.tzd`、`bench/py/round2.py`、`bench/js/round2.js`、`bench/java/Round2.java`。

## 分析

**JIT 强项依旧清晰**：`monteCarlo`（纯数值紧循环 + 顺序状态依赖）TzdLang 以 6.7 ms 全面夺冠，
领先 Java 2.1×、Node 3.3×、Python 89×——第一轮建立的非装箱数值代码路径在抗优化的
有状态循环上依然有效。

**数据结构基础设施是当前短板**：

1. **`qsort` 差距最大（对 Node 203×）**。7 秒 vs V8 的 34 ms。内核是「全局数组 + 递归 + 逐元素交换」，
   约 5M 次比较 + 1.5M 次交换 + 60 万次递归调用。TzdLang 摊到每次比较约 1.3 µs，
   说明递归调用未走原生快速路径、全局数组元素访问未做边界检查消除（第一轮 RESULTS.md 描述的
   Hoisted BCE 优化对这种「全局容器 + 深递归」形态未生效）。
2. **`oop`（对象分配 + 方法分发）对 Java/V8 慢约 60×**：每次迭代（4 步 LCG + 2 次分配 + 1 次调用）
   TzdLang 耗时 ~6.5 µs，Java ~106 ns。对象分配走堆装箱、方法调用走动态查表的概率高。
3. **`mapOps` 慢 29–42×**：每次 map 操作 + toString 键构造约 3.4 µs。哈希、键字符串、扩容路径均有开销。
4. **`stringBuild` 需要正确解读**：所有不可变字符串语言的累积拼接都是 O(n²) 总拷贝（本内核 ~1.28 GB 字节拷贝）。
   TzdLang 577 ms ≈ 2.2 GB/s 有效拷贝速率，其实已接近 memcpy 水平；Java 250 ms 是 JIT 化的
   `System.arraycopy`（~5 GB/s）；Node 6.5 ms 赢在 rope/cons-string 根本不拷贝。
   该内核量的主要是「字符串增长策略」而非拼接速度本身。

**一句话总结**：数值紧循环（无分配、无容器）TzdLang JIT 已是世界一流；一旦进入
对象/哈希表/数组重排等运行时服务密集的负载，与 JVM/V8 仍有 1.5–2 个数量级的差距。
下一阶段优化优先级建议：递归调用约定与全局数组访问的 BCE（qsort 形态）> 对象分配与
方法分发缓存（oop）> map/哈希路径（mapOps）。

## 本轮测试中发现并处置的 TzdLang 问题

| 问题 | 状态 | 复现脚本 |
|---|---|---|
| 顶层 `range(0, 5, 1)`（字面量实参）返回空数组 | **已修复**（07:31 构建，验证通过） | probe5.tzd |
| JIT 编译的函数内 map 下标写 → 硬崩（0xE06D7363；20 万条时 0xC0000005） | **已修复**（10:34 构建，验证通过） | probeM2.tzd |
| **数组作为函数实参传入后，函数内大小为 0**（写入报"数组下标越界…大小为 0"） | **仍存在**（10:34 构建复现） | probe4.tzd |
| 运行时错误的源码行号指向错误位置（如 mapOps 的错误指向 quickSort 的行） | 仍存在 | 任意内核报错时可见 |
| 顶层对已有变量赋对象值时回显 `>>> [Class: Stopwatch]` | 仍存在（轻微） | round2.tzd 首行 |

为绕过数组传参 bug，`qsort` 在四种语言中统一采用**全局数组 + `qsort(lo, hi)`** 结构（工作量完全一致）。
